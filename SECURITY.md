# Security policy

## Reporting a vulnerability

Use GitHub's private vulnerability reporting on this repository (Security tab, "Report a
vulnerability"). Include the recording or request that reproduces the issue. You will get an
acknowledgement within a week. Do not open a public issue for a vulnerability, and never test
injection, spoofing, or jamming against live aviation systems: `aero synth` and the demo
injections exist so that nothing real is ever touched.

## What this software is

aero-audit is a **passive** analysis tool. It reads public ADS-B feeds and imagery and writes
reports. It never transmits, never connects to aircraft, ATC, or airline systems, and holds no
credentials except optional OpenSky API client credentials in a git-ignored `.env`.

## The local app

The app (`aero app`, `aero demo`) is a web server on your machine. A server on 127.0.0.1 is
reachable by every web page you have open, so it defends itself
([`aero_audit/web/security.py`](aero_audit/web/security.py), tests in
[`tests/test_app_security.py`](tests/test_app_security.py)):

| Threat | Control |
|---|---|
| DNS rebinding (a remote page points its own hostname at 127.0.0.1) | `Host` header must be a loopback name or one passed with `--allowed-host` |
| Cross-site request forgery (a page you visit POSTs to the API) | every POST needs the per-process token in `X-Aero-Token`, which forces a CORS preflight the server never grants; `Origin` and `Sec-Fetch-Site` must be same-origin; body must be `application/json` and under 1 MB |
| Script injection through data (callsigns, reports, tile URLs) | strict Content-Security-Policy: no inline script, no eval, images only from OpenStreetMap; no inline event handlers in the front end; `nosniff`, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer` |
| Reading arbitrary files through parameters | every path is confined: recordings to `data/recordings` and `data/samples`, models to `models/`, watchlists to `data/`, logs to `logs/`; docs only from `docs/` and `README.md` |
| Sending findings to an attacker-chosen endpoint | webhook URLs must be `http(s)` without embedded credentials; the change is written to the audit log |
| Loading a malicious model (a pickle is code) | a model loads only when its SHA-256 matches `models/registry.json`, which only `aero train` writes; override needs `--allow-unverified-model` or `AERO_ALLOW_UNVERIFIED_MODEL=1` |
| Exposure beyond the machine | binding to anything but loopback requires `--token` / `AERO_APP_TOKEN` (then every API call is authenticated) or an explicit `--allow-unauthenticated`, meant for a container whose port the host publishes on 127.0.0.1 |
| Tampering with the record of what was done | the audit log is hash-chained (`aero log verify`); reports ship with a manifest of SHA-256 hashes and full provenance (`aero log verify-report`) |

What it does **not** do: there is no user login, no TLS, and no rate limiting. It is a single-user
desk tool. Putting it on a network for several people needs a reverse proxy with authentication
and TLS in front of it; the token mode is the minimum, not the design.

## Supply chain

- Dependencies are pinned with SHA-256 hashes in `requirements.lock.txt` (universal, generated by
  `make lock`). The bootstrap scripts, the Dockerfile and CI install with `--require-hashes`.
- CI runs `pip-audit` against the lock, `gitleaks` over the full history, CodeQL for Python and
  JavaScript, and builds the container. GitHub Actions are pinned to commit SHAs. Dependabot
  watches pip, actions and the base image.
- The container runs as a non-root user with all capabilities dropped and no build step: the
  package runs from source, so nothing unpinned is fetched at build time.
- Vision weights (`yolov8n.pt`) are fetched from the ultralytics GitHub release on first use of
  the optional `[vision]` extra; verify the checksum against the release page or vendor the file.
- The front end has no build step and one vendored library (Leaflet 1.9.4).

## Data handling

- Recordings contain public broadcast data but enable tracking of individuals' aircraft. Apply
  retention (`aero data prune`), keep recordings out of version control (they are ignored), and
  honour `protect` watchlist entries.
- The bundled samples in `data/samples/` are short adsb.lol captures published under the ODbL;
  see `data/samples/ATTRIBUTION.md`.
- Never place credentials in recordings, reports, or the audit log. Settings changes are logged
  with their values, so keep secrets in `.env`, not in Settings.
